# resident_interaction

## Purpose
Provide a single action request/result flow for player interactions with residents, resident details, office groups, dynamic events, career promotion, rumor discussion, and share-fish content.

## Main files
- `fishing_office_flutter/lib/models/interactive_office.dart`
- `fishing_office_flutter/lib/core/engine/second_world_engine.dart`
- `fishing_office_flutter/lib/core/providers/app_providers.dart`
- `fishing_office_flutter/lib/widgets/office/office_hub_dialog.dart`

## Invariants
- Duplicate `actionId` must be blocked.
- Unsupported action types return a safe blocked result.
- Resident actions use `interactWithResident`.
- Rumor actions activate rumor context and write resident memory through existing paths.
- Group actions use `RelationshipRuntimeManager.applyOfficeGroupInteraction`.
- Event actions use `DynamicEventRuntimeManager.triggerEvent` and `resolveEvent`.
- UI does not mutate wallet, inventory, tasks, achievements, relationships, stories, or events directly.
- Resident detail is a ViewModel projection only and must not save business state.
- Share fish requires an inventory-selected `fishId`; successful settlement deducts one fish through existing inventory state and records memory, friendship, skills, player action, and processed keys through existing runtime/save paths.

## Known limitations
- Current request ids are generated by UI time; deeper idempotency can be improved when product defines persistent interaction sessions.
- Resident detail UI is integrated into Office Hub, not a standalone page.
- Share fish uses item quantity rather than per-fish instance identity until inventory stores fish instances.
