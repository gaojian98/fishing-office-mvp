# v1.3.0 Long-Term World Evolution Design

## 1. 文档目的

本文是 Fishing Office 从“功能型游戏”进入“持续演化世界”的长期设计总纲。

它不是 Roadmap 的重复，也不是单一模块技术说明。它记录：

- 世界为什么这样设计。
- 各系统如何长期协同。
- 哪些规则必须长期保持稳定。
- 哪些边界未来版本不可轻易破坏。
- 为什么当前架构选择优于其他方案。
- v1.3.0、v1.4.0、v1.5.0、v2.0.0 如何连续演进。

后续 Codex 开发涉及 v1.3 世界演化设计时，应先读取本文，再读取具体 Module Manifest。

## 2. 产品长期愿景

Fishing Office 的长期目标不是不断增加独立功能，而是建立一个能够持续运行、持续变化、持续产生历史的办公室世界。

这个世界应逐步具备：

- 组织结构
- 居民职业生命周期
- 居民关系演化
- 自主决策
- 公司经济
- 长期记忆
- 公司事件
- 历史时间线
- 玩家影响
- 可恢复的持久状态

每个新模块都必须服务于“世界演化”，而不是成为孤立功能。

## 3. 世界演化核心原则

1. 世界状态必须连续演化，而不是每天重新生成。
2. 居民行为必须受组织、职业、关系、情绪、记忆和环境共同影响。
3. 玩家可以影响世界，但不能完全控制世界。
4. 公司和居民都应具备长期历史。
5. 事件应产生后果，而不是只显示一次文本。
6. 世界变化必须可保存、可恢复、可解释。
7. 所有长期历史都必须有容量边界。
8. 所有奖励和状态写入必须具备幂等性。
9. 模块之间通过统一 Context、Snapshot、RuntimeResult 协作。
10. UI 不直接计算核心业务规则。

## 4. 公司组织模型

当前组织模型采用：

Company -> Department -> Team -> Position -> Resident Assignment

### 设计理由

- 使用稳定 ID，因为显示名称会改名、翻译和本地化，不能作为主键。
- 职业变化必须同步组织归属，因为岗位、团队、部门和职业状态共同决定居民在公司中的真实位置。
- 岗位占用必须有一致性，因为同一岗位容量可能有限。
- 同一居民不能同时拥有多个有效岗位，否则 Dialogue、Story、Quest、Dynamic Event 会读取到冲突状态。
- 旧岗位释放与新岗位占用必须是同一事务，避免旧岗位已释放但新岗位未占用的半完成状态。
- 组织历史与当前组织状态需要分离，当前状态用于查询，历史用于时间线、记忆、新闻和回溯。

### 当前已确认规则

- IMPLEMENTED: 同团队晋升只更新岗位和层级。
- IMPLEMENTED: 跨团队晋升更新团队、岗位和汇报关系上下文。
- IMPLEMENTED: 跨部门晋升或转岗同步更新部门、团队、岗位。
- IMPLEMENTED: 降职按目标岗位重新分配。
- IMPLEMENTED: 离职释放岗位但保留 Resident 和历史。
- IMPLEMENTED: 入职必须绑定有效组织位置。

## 5. 居民生命周期

居民长期可能经历：

- IMPLEMENTED: 入职
- PLANNED: 试用
- IMPLEMENTED: 正式任职
- IMPLEMENTED: 晋升
- IMPLEMENTED: 转岗
- IMPLEMENTED: 降职
- PLANNED: 休假
- IMPLEMENTED: 离职
- PLANNED: 返聘
- DEFERRED: 退休

每个生命周期节点都应记录：

- 当前状态
- 历史状态
- 触发条件
- 对组织的影响
- 对经济的影响
- 对关系的影响
- 对新闻和时间线的影响
- 对存档的影响

尚未实现的状态不得写成已完成。

## 6. 职业成长模型

职业成长不能只由单一数值决定。

未来职业决策至少考虑：

- 能力
- 技能
- 绩效
- 关系
- 信任
- 组织岗位空缺
- 部门需求
- 公司经济
- 居民意愿
- 长期记忆
- 事件影响

### 设计理由

- 晋升不是简单等级 +1，而是组织需要、岗位容量、居民能力和事件后果共同作用。
- 转岗不是只修改字符串，而是释放旧岗位、占用新岗位，并更新上下文。
- 离职不是删除 Resident，而是组织任职失效、历史保留。
- 招聘不是凭空创建岗位，而是来自部门需求和岗位空缺。
- 职业历史必须保留，用于记忆、时间线、新闻和后续 AI 决策。
- 职业事件必须拥有 sourceId / mutationId，确保重复事件不重复结算。

## 7. AI 决策模型

后续 AI 决策必须遵循统一输入和输出。

### 输入

- 当前组织
- 当前岗位
- 职业状态
- 个性
- 情绪
- 关系
- 记忆
- 公司经济
- 动态事件
- 玩家影响
- 时间与环境

### 输出

- 决策
- 原因
- 置信度
- 影响对象
- 预计后果
- 是否可执行
- 是否需要冷却
- 是否写入历史

### 禁止

- UI 直接生成 AI 决策。
- 每 Tick 全量两两比较。
- 多个 Runtime 重复实现同一决策规则。
- AI 决策绕过组织和职业校验。
- AI 决策直接修改多个模块状态而没有统一事务。

## 8. 公司经济模型

公司经济未来应影响：

- 招聘
- 工资
- 奖金
- 晋升
- 裁员
- 项目预算
- 部门扩张
- 培训
- 公司事件

### 边界

- 公司经济不能与玩家背包经济混为一体。
- 公司账务与居民个人收入需要分离。
- 同一结算周期必须幂等。
- 工资、奖金、成本和收益必须有稳定结算键。
- 经济历史必须有限长。
- 经济系统不能在每 Tick 重算全部历史。

## 9. 长期记忆模型

长期记忆分层：

- 短期互动记忆
- 关系记忆
- 职业记忆
- 组织记忆
- 事件记忆
- 玩家记忆
- 公司历史记忆

每类记忆至少定义：

- 触发来源
- 保留时间
- 重要度
- 容量上限
- 是否影响决策
- 是否进入 UI
- 是否进入存档
- 如何过期
- 如何压缩

长期记忆禁止无限增长。

## 10. 公司新闻与时间线

Company News 和 Company Timeline 必须分离。

Company News 是面向玩家展示的可读信息。

Company Timeline 是面向世界状态和历史查询的结构化记录。

### 原则

- 新闻可以合并、摘要和本地化。
- 时间线必须保留稳定事件 ID。
- 同一事件不得重复写入。
- 新闻不应成为唯一数据源。
- UI 展示依赖时间线快照，而不是直接扫描全部 Runtime。
- 每日、每周、每月、季度和年度信息应分层汇总。

## 11. 世界事件模型

事件至少包含：

- eventId
- sourceId
- type
- scope
- participants
- cause
- conditions
- effects
- startTime
- endTime
- status
- cooldown
- historyResult

事件可能影响：

- 组织
- 职业
- 关系
- 情绪
- 经济
- 决策
- 新闻
- 时间线
- 玩家任务

事件不得直接绕过对应 Runtime 的校验和事务接口。

## 12. 玩家影响边界

玩家可以：

- 与居民互动
- 影响关系
- 分享资源
- 参与事件
- 影响声誉
- 间接影响职业与组织决策

玩家不能：

- 无条件直接改写所有居民状态。
- 绕过岗位容量。
- 绕过经济条件。
- 强制跳过冷却。
- 直接修改历史。
- 重复领取奖励。
- 破坏世界自主性。

长期目标：玩家是世界中的参与者，不是全能管理员。

## 13. 世界状态与 Tick 关系

- 不默认修改现有 Tick 顺序。
- 明确事件发生时才执行组织或职业 Mutation。
- UI 打开页面不得触发完整 Tick。
- 查询与状态变更必须分离。
- 高频 Tick 只执行轻量任务。
- 重型计算按日、周、月分层执行。
- 100 居民规模保持稳定。
- 禁止常规 O(n²) 路径。
- 可使用索引、分桶、活动居民集合和缓存。

## 14. Save / Restore 兼容原则

1. 新字段必须有默认值。
2. 旧存档缺失字段必须安全恢复。
3. 不删除旧 Resident。
4. 当前状态与历史状态分离。
5. 恢复后岗位占用必须一致。
6. 恢复后不能重复发放奖励。
7. 恢复后不能重复晋升、工资、新闻、事件。
8. sourceId / mutationId 必须保存。
9. 历史数据必须有限长。
10. 新版本迁移必须可检测、可回退或安全 fallback。

## 15. 性能与规模边界

当前目标规模：

- 100 位居民稳定运行。
- 未来可扩展到更高规模，但不作为 v1.3.0 强制目标。
- 常规 Tick 不得 O(n²)。
- 组织、岗位和居民查询优先索引化。
- 长期历史必须分页或截断。
- UI 只读取 Snapshot。
- 页面不得全量扫描全部世界数据。
- 多模块不得重复构建相同快照。
- 缓存必须具备失效条件。

## 16. UI 与 Runtime 边界

UI 负责：

- 展示
- 输入
- 状态反馈
- Loading
- Error
- Disabled
- 导航

Runtime 负责：

- 规则
- 校验
- 决策
- 状态变化
- 事务
- 幂等
- 历史
- Snapshot

Provider 负责：

- 连接 Runtime 与 UI
- 本地刷新
- 状态订阅
- 错误转换

UI 禁止直接：

- 晋升居民
- 修改组织归属
- 发工资
- 写历史
- 生成新闻
- 处理幂等
- 计算 AI 决策

## 17. 数据与 JSON 边界

JSON 适合：

- 静态配置
- 文案
- 基础模板
- 初始内容
- 可运营内容

JSON 不适合：

- 当前居民状态
- 当前岗位占用
- 实时经济账务
- 动态关系
- 运行历史
- 事务状态
- 幂等记录

运行态数据必须进入 Save / Runtime State。

## 18. 模块协作方式

未来模块依赖链：

Company Organization -> Career Growth -> Office Economy -> AI Decision -> Long-term Memory -> Company News -> Company Timeline -> AI Company Events -> Office Analytics -> QA / Performance / Release

### 模块职责

- Company Organization 是共享基础。
- Career 负责职业状态。
- Economy 负责经济约束。
- AI Decision 负责决策。
- Memory 提供长期上下文。
- News 负责可读输出。
- Timeline 负责结构化历史。
- Events 负责跨模块影响。
- Analytics 只读聚合，不直接修改业务状态。

后续模块不得绕过前置模块。

## 19. 版本演化路线

### v1.3.0: Living AI Company 基础

- 主要目标：组织、职业、组织变更事务、长期设计文档。
- 依赖前置：v1.2.0 Interactive Office Life。
- 不应提前实现：完整公司经济、完整 AI 决策、多公司世界。
- 迁移重点：旧存档组织和职业字段 fallback。
- 性能重点：100 居民稳定运行，不引入 O(n²) 常规 Tick。
- 存档重点：mutation sourceId、当前状态和历史状态分离。

### v1.4.0: Autonomous Resident Decisions

- 主要目标：居民自主决策开始读取组织、职业、关系、记忆和环境。
- 依赖前置：v1.3.0 组织和职业一致性。
- 不应提前实现：不可解释黑箱决策、大规模多公司模拟。
- 迁移重点：决策历史和冷却字段默认值。
- 性能重点：按活动居民、地点、部门分桶，不做全量两两比较。
- 存档重点：决策 sourceId、冷却、后果历史。

### v1.5.0: Advanced Company Economy & Social Evolution

- 主要目标：公司经济、工资、预算、奖金、部门扩张和社会关系长期演化。
- 依赖前置：v1.4.0 可解释决策。
- 不应提前实现：真实财务系统或与玩家背包经济混同。
- 迁移重点：经济账期、结算键、历史压缩。
- 性能重点：按日、周、月分层结算，不每 Tick 重算历史。
- 存档重点：账期幂等、工资和奖励去重。

### v2.0.0: Persistent AI Office World

- 主要目标：长期可持续、可恢复、可解释的办公室世界。
- 依赖前置：组织、职业、AI 决策、经济、记忆、新闻、时间线全部形成闭环。
- 不应提前实现：未验收的大规模世界扩容。
- 迁移重点：长期历史压缩、多版本存档兼容。
- 性能重点：Snapshot、索引、分页历史和后台任务边界。
- 存档重点：世界历史、新闻摘要、时间线和关键事件恢复一致。

## 20. 禁止事项

- 禁止无限制增加一级 Manager / Engine / Repository。
- 禁止多个 Runtime 重复实现同一规则。
- 禁止 UI 直接修改核心状态。
- 禁止每 Tick 全量 O(n²)。
- 禁止无限增长历史。
- 禁止同一奖励重复结算。
- 禁止通过显示名称关联数据。
- 禁止组织、职业和经济状态彼此不一致。
- 禁止修改已发布 Tag。
- 禁止用 Production 作为测试环境。
- 禁止在未验收时直接 Merge main。
- 禁止将计划内容写成已实现。
